# Read-only and least-privilege guidance

Give each profile the smallest provider-native read-only role set needed by its selected domains. Restrict the profile to named accounts/projects/subscriptions and regions in `config.yaml`. `services` is enforced by `scopedAdapter` as a normalized result filter against the row's domain/service; it is not provider IAM and does not guarantee cloud API pushdown, so enforce the same restriction in provider IAM. Use separate profiles for production and non-production scopes when possible.

## Required properties

- Use the provider SDK's default credential chain, shared read-only profile, workload identity, or instance/task identity.
- Deny all write, mutate, delete, create, update, attach, detach, execute, and impersonation actions unless a provider's read-only role model includes them as harmless metadata reads.
- Permit only the inventory/resource-graph/resource-center operations that the installed `cloud_schema` reports for the selected domains. The current seven adapters expose 63 product-level native operations (the same nine suffixes for each provider) over the base inventory backends below, with a separate GCP IAM policy-search operation. Product names do not add service-detail SDK calls or data-plane permissions; scope the backend further to the configured account, project, subscription, view, or region where the provider supports that boundary. The separate seven compute-detail and 14 managed database/Kubernetes detail operations require only their fixed provider read actions listed below.
- If `metrics` or `costs` is used, add only the provider-specific read permissions in the connector baseline below. These are DSL connector calls, not `cloud_native_read` operations, and their implemented status does not prove live credentials, permissions, or data. The 63 product operations do not expose metrics or costs. The service never reads metric/log event bodies, object bodies, database rows, messages, secrets, or credentials.
- Logging metadata may be classified from inventory responses, but no log-event connector is active. Do not grant object read, database-data read, message consume, secret-value read, log-event read, or Kubernetes API credentials for this control-plane service.

### Product-level native operation boundary

Each provider registers the nine product-level names documented in [docs/tools.md](tools.md): `compute.list_instances`, `compute.list_disks`, `storage.list_buckets`, `network.list_resources`, `iam.list_resources`, `database.list_resources`, `kubernetes.list_resources`, `monitoring.list_alarms`, and `logging.list_resources`. Across seven providers this is 63 operations. They delegate to the inventory backend in the table above, then filter normalized rows for the requested domain/kind after each provider page. An empty `rows` array therefore does not prove that the scan is finished when `next_cursor` is still present.

| Provider | Product operation prefix | Permission boundary |
| --- | --- | --- |
| AWS | `aws.` | Same `resource-explorer-2:Search` permission as the base inventory operation. |
| GCP | `gcp.` | Resource products use `cloudasset.assets.searchAllResources`; `gcp.iam.list_resources` uses `cloudasset.assets.searchAllIamPolicies`; both also require `serviceusage.services.use`. |
| Azure | `azure.` | Same `Microsoft.ResourceGraph/resources/read` and underlying resource read boundary as the base graph operation; the IAM product view uses the graph's authorization-resource query. |
| Alibaba Cloud | `alibaba.` | Same `resourcecenter:SearchResources` permission as the base Resource Center operation. |
| Huawei Cloud | `huawei.` | Same `rms:resources:list` permission as the base RMS operation. |
| Tencent Cloud | `tencent.` | Same Cloud Resource Center read role/action boundary as the base `SearchResources` operation; confirm the exact CAM action in the target account. |
| Volcengine | `volcengine.` | Same `resourcecenter:SearchResources` permission as the base Resource Center operation. |

Do not grant separate compute, storage, database, monitoring, logging, or Kubernetes service-detail permissions merely because a product operation name contains that domain. The operation schemas are typed filters only; they do not permit arbitrary actions, URLs, SDK method names, or raw provider query strings. AWS product operations have no `params`; their region is the top-level native-read `region` field. The seven compute and 14 managed database/Kubernetes detail operations are separate fixed service reads and do require the corresponding detail permission sections below. Metrics and costs remain DSL-only and require the separate connector permissions below.

The detail calls require no object read, database-data read, database endpoint/connection-string access, Kubernetes API credential, kubeconfig, certificate, token, secret, log-event, message, or write permission. They return only bounded normalized metadata, including optional provider-specific `attributes.posture` and unique, primary-response-only `attributes.related` identifiers capped at 100 per key. Schemas reject undeclared parameters and cursors; no recursive/follow-up graph query is authorized. These details are live-unverified, and any unresolved RAM/IAM/CAM action or built-in-reader mapping must be confirmed with each target provider's policy tooling before live acceptance.

## Metrics and billing operation baseline

The following are the only metric and billing calls currently made by the seven adapters. They are invoked by the DSL `metrics`/`costs` sources and are not registered `cloud_native_read` operations. Use the narrow action/custom role where the provider supports it, then add the underlying service read actions required by the provider's metric index. Cost amounts remain in the source currency; Tencent's currency is a profile declaration because its response omits currency. Region semantics are source/provider-specific: Azure metrics require an exact region and send it as the provider parameter; GCP IAM/metrics are global for the selected project and do not fan out by region; all costs use one global/account/project-level call per expanded target and filter any explicit region locally in normalized rows. `LIVE VALIDATION REQUIRED` means the operation is implemented but the exact IAM action or built-in reader must still be confirmed in the target account before live acceptance.

| Provider | DSL connector and official read-only API | Minimum read action / permission | Built-in reader or prerequisite |
| --- | --- | --- | --- |
| AWS | `aws.cloudwatch.get_metric_data` → CloudWatch `GetMetricData`; `aws.costexplorer.get_cost_and_usage` → Cost Explorer `GetCostAndUsage` | `cloudwatch:GetMetricData`; `ce:GetCostAndUsage` | `CloudWatchReadOnlyAccess` is the AWS managed CloudWatch reader. Costs: `bigquery.jobs.create` on the query project and `bigquery.tables.getData` on the export table/dataset | Metrics require `scopes.projects` or a project-level `options.asset_scope`; missing project scope is `not_configured`. `roles/monitoring.viewer` is the documented baseline. The GCP BigQuery prerequisite is intentionally explicit: the principal needs `bigquery.jobs.create` in the project used for the query job and `bigquery.tables.getData` (normally through `roles/bigquery.dataViewer`) on the pre-existing Billing Export table or dataset. The service never enables export, creates a dataset, writes table rows, or reads unrelated tables. Azure Cost Management uses a POST query operation for a read-only cost report; no cost configuration is changed. Huawei `billing_site` is required and only selects the endpoint; omission leaves the cost capability `not_configured` and the query unavailable. Huawei metrics use a project scope as `project_id`. Tencent `billing_currency` is a user assertion and must match the account's billing currency; both Tencent metrics and costs require exactly one account scope, and metrics also require an exact non-`*` region. AWS metrics use the selected account as CloudWatch `AccountId`; Alibaba and Volcengine metrics likewise require exactly one account scope. Cost connectors do not promise region pushdown: each expanded account/project/subscription target makes one global/account-level billing call and the engine applies explicit region constraints locally to normalized rows.

## Credential hygiene

Never put secrets in YAML, DSL literals, MCP arguments, shell command lines, README examples, or issue reports. The only credential sources are `default`, `profile`, `env`, and `workload`; `profile` names an AWS shared profile only. Refer to a shared profile or environment variable name; keep the value in the provider credential store or deployment secret manager. For GCP service-account JSON, set `GOOGLE_APPLICATION_CREDENTIALS` outside this configuration and reference that variable name through `credential.env`; never embed JSON or a private key. Do not enable debug logging that prints SDK requests or authorization headers.

`cloud_profiles` must be safe to call from an untrusted client: it reports provider, profile, scope, regions, and readiness only. Audit logs should contain query ID/profile/operation/timing/count/status, never request bodies, credentials, raw provider payloads, object/database/log contents, or secret values.

## Validation checklist

1. Run `validate-config` and inspect only non-secret validation output.
2. Call `cloud_schema` and record the exact registered operations for the deployment.
3. Call `cloud_explain` for each planned query and check the target scope and capability notes or configuration requirements.
4. Run representative `cloud_query` calls against a test or read-only production profile.
5. Review provider audit logs and confirm every call was a read operation in the expected account/project/subscription and region.
6. Remove profiles or narrow scopes that are not required for the workload.
