# Provider capability and readiness

The server has one normalized provider contract and a read-only operation registry. All seven provider adapters implement control-plane resource inventory and expose the same nine product-level native suffixes, yielding 63 provider-qualified operations. Those operations use each provider's fixed inventory, resource graph, or resource center backend and return normalized metadata; they are not service-detail SDK operations. Each adapter also exposes one service-level compute-instance detail operation and two managed database/Kubernetes detail operations backed by fixed provider service read APIs. The adapters also implement DSL-only metric and cost connectors against the provider APIs listed below. `cloud_schema` separates the static `capability_matrix` (compiled seven-provider by four-source baseline) from `profile_capabilities` (configured-profile status and prerequisites); `operations` lists native operations registered by currently configured profile adapters. Resource capability status `inventory` describes metadata coverage, not comprehensive service coverage; all 21 detail operations are registered read operations but remain live-unverified. Metrics and costs normally report `available`; GCP costs report `not_configured` until `options.billing_table` is supplied, Tencent costs report `not_configured` until both `options.billing_currency` and exactly one `scopes.accounts` entry are supplied, and Huawei costs report `not_configured` until `options.billing_site` is explicitly set to `china` or `intl`. A missing Huawei billing site makes a cost query return `capability_unavailable`. Alibaba, Tencent, and Volcengine metrics report `not_configured` when `scopes.accounts` is missing or contains more than one account; Tencent metrics also require a non-`*` exact profile region. Huawei metrics require a `scopes.projects` target and bind its project ID to CES credentials; a missing project scope reports `not_configured`. AWS metrics pass a selected account scope to CloudWatch as `AccountId`. These statuses describe compiled/profile configuration, not live access. Account permissions, region, service enablement, data retention, inventory/service availability, exact scope, and representative resource presence still determine whether a query succeeds.

## Service-level compute instance details

The following seven operations are service-level, read-only detail reads, not additional inventory product suffixes. Each targets one named compute instance through the provider's fixed compute API and returns one normalized row. They are live-unverified in this checkout.

| Provider | Exact operation | Fixed read API | Required parameters and scope |
| --- | --- | --- | --- |
| AWS | `aws.ec2.describe_instance` | EC2 `DescribeInstances` | `params.instance_id`; top-level exact `region`; exactly one profile account. |
| GCP | `gcp.compute.instances.get` | Compute Engine `instances.get` | `params.project_id`, `params.zone`, `params.instance`; project must be allowed by the profile. |
| Azure | `azure.compute.virtual_machines.get` | Compute virtual-machine resource read | `params.subscription_id`, `params.resource_group`, `params.name`; subscription must be allowed by the profile. |
| Alibaba Cloud | `alibaba.ecs.describe_instance_attribute` | ECS `DescribeInstanceAttribute` | `params.instance_id`; top-level exact `region`; exactly one profile account. |
| Huawei Cloud | `huawei.ecs.show_server` | ECS `ShowServer` | `params.project_id`, `params.server_id`; project must be allowed by the profile; top-level exact `region`. |
| Tencent Cloud | `tencent.cvm.describe_instances` | CVM `DescribeInstances` | `params.instance_id`; top-level exact `region`; exactly one profile account. |
| Volcengine | `volcengine.ecs.describe_instances` | ECS `DescribeInstances` | `params.instance_id`; top-level exact `region`; exactly one profile account. |

Detail output is limited to common identity/scope/state fields and provider-supplied stable attributes: instance type, CPU and memory when supplied, image, network/VPC/subnet and private/public IPs, security-group information when supplied, OS, and billing mode. Missing provider values are not filled from arbitrary metadata. UserData/customData, arbitrary metadata, admin/password material, console/VNC access, credentials, other data-plane fields, and complete SDK responses are excluded. The managed database and Kubernetes detail operations below are a separate service-level catalog and do not change this compute boundary.

The detail schemas are closed and reject undeclared parameters and continuation cursors. Each operation makes one fixed provider request and returns one normalized metadata row; it never performs recursive or follow-up graph queries. `attributes.posture` is an allow-listed, provider-specific map whose keys are optional when the provider response does not supply the value. It is not a universal posture schema: GCP Cloud SQL uses `customer_managed_encryption_key_enabled`, and AWS RDS `logging_enabled`/`audit_enabled` are only emitted when CloudWatch log-export entries are present, with `audit_enabled` requiring an audit export. `attributes.related` contains unique identifiers from the primary response only, with a maximum of 100 identifiers per key.

The service-level result never returns a password, connection string, database endpoint, kubeconfig, certificate, token, secret, `user_data`, logs, database rows, message/body, or a complete SDK response. Provider-specific identity, state, version, network, billing, and posture fields remain optional and are not filled from arbitrary metadata. Database/Kubernetes detail permissions are separate from the inventory baseline and are documented in [docs/permissions.md](permissions.md); any action or reader mapping not established there is explicitly `LIVE VALIDATION REQUIRED`.

## Metrics and cost connectors

These are invoked through `cloud_query`/`cloud_explain` for the `metrics` and `costs` sources. They are not arbitrary native operations and are not callable through `cloud_native_read`. Every row and API result is still subject to the configured profile scope, region, service filter, request limits, and normalized-field allow-list. Region execution is source/provider-specific: Azure subscription metrics require and push an exact region query parameter; GCP IAM/metrics use one global project target without region fan-out; and costs use one global/account/project-level call per expanded target, with an explicit DSL region constraint applied to normalized rows locally. `implemented; live unverified` means the connector is present in this checkout but has not been exercised with a real profile.

## Common read-only boundary

The inventory normalizer can classify returned resources into these common domains and kinds. This is inventory metadata coverage, not a claim that each provider has a separate connector for every service:

- Compute: VM instances and block disks.
- Storage: bucket metadata; never object bodies.
- Network: VPC/VNet, subnets, security groups/firewalls, public IPs, and load balancers.
- IAM: cloud-native users, roles, service accounts, policies, and bindings; enterprise directories are outside this scope.
- Database: managed relational instances and Redis-like caches; never database rows.
- Kubernetes: managed clusters, node pools, versions, network/control-plane metadata; never kube-apiserver access.
- Monitoring: `monitoring.list_alarms` returns normalized alarm/configuration metadata when the inventory backend exposes it. Metric time-series rows remain available only through the provider connectors above; selector syntax and range bounds are documented in [docs/dsl.md](dsl.md).
- Logging: `logging.list_resources` may classify logging projects, groups, indexes, or sinks from inventory metadata; no log events are read.
- Costs: daily/monthly normalized billing rows through the provider connectors above; costs remain DSL-only. GCP uses a user-prepared Billing Export table and does not create or enable exports.

Cost region semantics are uniform across the adapters: each expanded account/project/subscription target makes one global or account-level billing call, and an explicit DSL `scope region` is applied to the returned normalized rows locally. A region in the profile or query is therefore not evidence of billing API pushdown.

Only the operations present in the runtime registry are callable through `cloud_native_read`. That tool does not accept arbitrary SDK method names, action strings, HTTP methods, URLs, or provider query languages. The 63 product-level operations accept only the exact typed schemas in [docs/tools.md](tools.md); their top-level `region` and profile scope remain enforced independently of `params`. Product filters are applied to normalized rows after a provider page, so an empty product page can still carry a non-empty `next_cursor`. The seven compute-detail and 14 managed database/Kubernetes detail operations accept only their exact parameters and scope, reject cursors and list-style expansion, and return one normalized metadata row. Detail permissions are separate from inventory permissions and are listed in [docs/permissions.md](permissions.md). Neither operation class returns service data-plane content. DSL metric selectors are parsed by the server and routed only to the fixed connector above; metrics and costs remain DSL-only and are not provider-native operation injection. Unsupported configuration or coverage is reported as `not_configured`, a provider capability error, or a per-target error, not silently approximated with a write-side or raw-response path.

## Provider setup dependencies

Inventory APIs and resource graph/center services are often separately permissioned or enabled. The 63 product-level operations reuse the inventory permission baseline for the provider backend; they do not require separate service-detail List/Describe permissions, and they never read object bodies, database rows, log events, or Kubernetes API data. The seven compute and 14 managed database/Kubernetes details use separate fixed service read APIs and therefore need separate provider read permissions; they still return only one allow-listed metadata row and never data-plane content. Metric and billing APIs are separately permissioned and may have their own retention, region, subscription, or account constraints. GCP metrics require `scopes.projects` or a project-level `options.asset_scope`; GCP IAM/metrics are global for the selected scope and do not fan out by region. GCP costs require a user-prepared standard Billing Export table. Azure metrics require an exact profile region and push it as the required API parameter, while Azure costs are subscription-level and filter region locally. Alibaba, Tencent, and Volcengine metrics require exactly one configured account; Tencent metrics additionally require an exact non-`*` region, and Tencent costs require that single account plus a declared currency. AWS metrics use the selected account as CloudWatch `AccountId`. Huawei metrics require a project scope bound as `project_id`; Huawei costs require an explicit `billing_site` of `china` or `intl`, with no default. All cost connectors make one global/account/project-level call per expanded target and apply any DSL region scope locally; a region setting is not guaranteed billing API pushdown. The server does not enable services, create resources, alter IAM, or create billing exports. A successful `cloud_profiles` response means only that a configured profile was discovered; it is not proof that inventory, metric, billing, or detail access is authenticated or that every product domain is accessible.

Before a live acceptance run, prepare one read-only profile per provider, at least one representative resource for each selected inventory domain, one representative compute instance, one managed database, and one managed Kubernetes cluster for the matching detail operations, representative metric time series, billing data for the requested dates, the required inventory/resource-graph/resource-center/compute/database/Kubernetes/metric/billing service access, and provider audit access to confirm only read calls occurred. Record the 63 product operations, seven compute-detail operations, and 14 managed database/Kubernetes detail operations as implemented but live-unverified until those checks are complete.
